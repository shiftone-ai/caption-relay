# UDトークの編集通信：公開資料で確認できた範囲

確認日：2026-10-07

**別アプリからUDトークの認識結果を訂正する実装例はある。現在の編集用共有URLを使う自作クライアント向けの通信仕様は、今回調べた公開資料では見つからなかった。**

純正Mac / Windows版のバイナリ解析と、元のWindows DLLによるオフライン実行結果は[編集通信の解析](udtalk-editor-protocol.md)に記録した。この資料は公開文書と公開ソースの調査結果であり、自作クライアントからの送信成功を示すものではない。

## 1. 純正編集クライアントで確認できる操作

Mac / Windows版は、公開トークURLを接続先へ追加して参加する。トーク側が編集を許可している場合は編集参加を選べる。既存発話の本文を変更し、Enterで送信・確定できる。編集中の途中更新、ほかの参加者による編集ロック、切断時のロック解除も説明されている。[接続ガイド](https://service.udtalk.jp/apps/udtalk-pc/connect/index.html)、[発話の編集ガイド](https://service.udtalk.jp/apps/udtalk-pc/utterances/index.html)

この操作説明から、AIを編集参加者として接続し、表示・字幕出力を純正側に任せる構成は検証する価値がある。ただし、操作説明だけでは共有URLの解析方法、認証情報、HTTP要求、本文のデータ形式を確定できない。

公式の2020年の記事でも、編集権と認識・直接入力中の状態を別々に扱い、編集確定によって翻訳処理が動くことを説明している。本文だけを送る実装では、確定状態やロックの扱いを取り違える可能性がある。[通信上のエラーへの対応と操作](https://udtalk.jp/post-4264/)

## 2. 純正以外の編集システムという先例

公式の連携アプリ一覧は、ITBC2と「まあちゃん」をUDトークと接続できるノートテイクシステムとして挙げている。[公式の連携アプリ一覧](https://udtalk.jp/relations/)

「まあちゃん」開発者の森直之による論文では、UDトークのTCP/IP接続に参加して認識結果を受け取り、内部データベースへ保存して発話の位置を再現する実装を説明している。親となる端末が編集を制御し、許可された端末だけが編集する。遠隔で訂正し、UDトークのQRリンクによるHTTP字幕閲覧と会場投影を併用した実験も報告されている。これは、純正アプリ以外の編集システムと純正の表示経路を組み合わせた先例である。[森直之「音声認識併用型遠隔文字支援システムの構築」第3.1節・第4節、紀要掲載2017年2月](https://caption-sign.jp/wp-content/uploads/2016/01/kiyo_2016_suw_yomi.pdf)

論文はメッセージのフィールドや現在のクラウド接続APIを公開していない。過去のLAN / VPN接続の説明を、そのまま現在の共有URL通信へ適用する根拠にはできない。

現在公開されている「まあちゃん」の配布ページも、通信仕様が変更されること、古い版が使えなくなる場合があることを明記している。Release 91のパッチにはQR通信の応答安定化が記載されている。[開発者の配布・更新履歴](https://machanbazaar.com/%E3%83%80%E3%82%A6%E3%83%B3%E3%83%AD%E3%83%BC%E3%83%89/)

## 3. 見つかった公開APIを取り違えない

| 公開物 | 実際に説明している通信 | 今回の訂正送信に使えると確認できたか |
| --- | --- | --- |
| 「まあちゃん」M5Stack連携例 | ローカルの「まあちゃん」APIへWebSocketで接続し、字幕の受信や送出操作を行う。例の接続先はポート50000 | UDトークへの直接接続や既存発話の訂正形式は示していない |
| ゆかコネNEOの本体API | ゆかコネへの文字入力、字幕受信、設定変更 | UDトーク側への既存発話の訂正APIは確認できない |
| ゆかコネNEOのプラグイン開発キット | プラグインからゆかコネへ文字列を渡す内部インターフェース | UDトークの共有URL・編集通信の実装は含まれていない |
| `ShamrockRecords/udtalk-apn` | 端末登録・参加状態・新規発話のプッシュ通知 | 認識結果の本文を訂正するサービスではない |

根拠：[M5Stack連携例の公開コード](https://note.com/mori_n/n/n13cbe206f826)、[ゆかコネNEO本体API](https://nmori.github.io/yncneo-Docs/tech/tech_api_neo/)、[プラグイン開発キットREADME](https://github.com/nmori/YNCNeo_Plugin/blob/f66aedd7c700e9951e277fd4988db44b0463e01c/README.md)、[UDトークの通知サービスREADME](https://github.com/ShamrockRecords/udtalk-apn/blob/6f61222e0ee083aeacddd749e8d4f2a4d42946cd/README.md)、[同サービスのルート実装](https://github.com/ShamrockRecords/udtalk-apn/blob/6f61222e0ee083aeacddd749e8d4f2a4d42946cd/routes/api.js)

`udtalk-apn`の名称にある「プッシュ」は端末への通知である。公式の公開案内も、公開トークを扱うサーバーとは別の通知サーバーとして説明している。[公式のソース公開案内](https://udtalk.jp/post-5088/)

検索語には「UDトーク 通信仕様」「UDトーク プロトコル」「UDTalk protocol」「UDTalk edit」「ITBC2 ソースコード」「まあちゃん ソースコード」を使用した。現在確認できる公開リポジトリ一覧では、まあちゃん本体やUDトーク編集クライアント本体のソースは見つからなかった。公開APIが存在しないと断定する結果ではない。

次の5点は、公開資料だけでは確定できない。URL解析とHTTP要求の形式は、その後の[バイナリ解析](udtalk-editor-protocol.md)で確認した。実接続と純正画面への訂正反映は未確認である。

1. 編集用共有URLの形式と、閲覧用URLとの権限の違い。
2. 接続・参加時に必要な識別子と認証情報。
3. 発話IDを使った編集ロックの取得・解放。
4. 途中更新と確定更新の要求形式、応答とエラー。
5. 現行クライアントと独自クライアント間で訂正が同期すること。

**次の検証は、公開サービスの障害復旧後に、本人が作成した試験トークへ純正編集クライアントで参加し、1件の発話を訂正する通信を観測すること。** 2026-10-07の公式障害告知と実接続の失敗は[編集通信の解析](udtalk-editor-protocol.md)に記録した。その要求と応答を確認してから、同じ試験トークに限定して独自クライアントの送信を検証する。
