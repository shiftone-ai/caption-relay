# UDトークのWeb字幕を取り込む

UDトークの「ウェブで公開」で発行する閲覧リンクから、新しい発話を取り込む実験用Adapterを用意した。公開APIとして保証された連携ではなく、公式Web表示の実装を観察して接続している。通常の起動では接続しない。

接続準備と公式配信コードの確認日：2026-10-06。

## 接続する

1. 音声認識を行うUDトークで、テスト専用トークを開く。Mac／Windows用の編集アプリには認識機能がない。今回の実機はApple SiliconのMac上で動くiOS版UDトークver.344。
2. 「Open Talk」→「Open Talk」→「Publish」でWeb閲覧リンクを発行する。現行Adapterはパスコード付きトークに対応していないため、機密情報を含まない接続試験で使う。
3. 閲覧リンクを環境変数に渡してサーバーを起動する。操作画面と観客画面を開き、UDトークの「Tap to Talk」から発話する。
4. `/api/source/udtalk` の `state` と `received_events`、操作画面の原文、観客画面の表示を確認する。`live` は閲覧接続が応答した状態であり、音声認識の成功を意味しない。
5. 試験終了時はUDトークの認識とWeb公開を停止し、Caption Relayのサーバーも終了する。

```bash
read -r -s CAPTION_RELAY_UDTALK_URL
export CAPTION_RELAY_UDTALK_URL
bash scripts/dev.sh
```

`read` の入力待ちで実際の `https://live.udtalk.jp/…` リンクを貼り付ける。リンクは閲覧権限を持つため、PR、ログ、スクリーンショットには含めない。設定したシェルを終了するか `unset CAPTION_RELAY_UDTALK_URL` で解除する。`.env` は起動スクリプトが読み込まない。

Caption Relayは引き続き `127.0.0.1` の単一プロセスで動かす。実機にCaption Relayの入力APIを公開する必要はない。Adapterが公式サービスへHTTPSでアクセスし、受信結果を同じプロセスの `CaptionRelay.source_event()` へ渡す。

## Macで合成音声を認識させる

今回の実機では、[BlackHole](https://github.com/ExistentialAudio/BlackHole)の2chデバイスにMacの合成音声を出力し、UDトークのマイク入力として認識させた。UDトークver.344の確認した設定には、任意の入力デバイスを選ぶ項目が見つからなかったため、Macの標準入力を一時的に変更した。出力先は合成音声の再生時に指定し、Macの標準出力は変更しなかった。

1. 現在のMacの入力デバイスを記録し、「サウンド」の入力を「BlackHole 2ch」に変更する。
2. テスト専用トークのWeb公開とCaption Relayへの接続を開始し、UDトークで日本語の認識を開始する。
3. 以下で出力デバイスを一覧にし、「BlackHole 2ch」の数値IDを入力する。IDは環境によって異なる。今回の環境では名前を直接指定すると再生に失敗したため、数値IDを使った。
4. 認識結果が操作画面と観客画面に届くことを確認する。
5. UDトークの認識とWeb公開、Caption Relayを停止し、Macの入力を記録したデバイスへ戻す。

```bash
say -a '?'
read -r BLACKHOLE_DEVICE_ID
say -a "$BLACKHOLE_DEVICE_ID" -v Kyoko -r 150 'キャプションリレーの音声認識テストです。本日はありがとうございます。'
```

背面での画面操作で認識の開始・停止とWeb公開を操作できた。UDトーク側の文字訂正はEnterによる確定でウィンドウのフォーカスを要求されたため、背面操作だけでは送信を確認できなかった。合成音声の認識は、物理マイクでの会話や会場の音響の検証には含めない。

## 確認した配信経路

| 根拠 | 確認内容 |
|---|---|
| [公式ダウンロード](https://udtalk.jp/download/) | iOS／Androidが認識元、Mac／Windows用編集アプリは認識・翻訳を行わない |
| [公式のWeb公開案内](https://udtalk.jp/post-3951/) | アプリがない端末でもブラウザで字幕を閲覧できる |
| [公式の公開セキュリティ案内](https://udtalk.jp/post-3953/) | 閲覧リンクの共有とパスコードの意味 |
| [公式Web表示の配信コード](https://live.udtalk.jp/js/app.js) | 初期化、閲覧参加、HTTP取得、発話内断片、認識段階、時刻、切断処理 |

参照コードのSHA-256は `6713e220d52fd75b6a7ca868a43be4cb07f43d22fae63ba41e0175502452fd45`。将来同じURLの内容が変わる可能性がある。

閲覧ページの埋め込みトーク情報を取得し、`app.udtalk.jp` に対して `checkAuth`、`initialize`、`webTalk`、`signWebTalk`、`webTalkCurrent`、`webTalkMessage` を順に使う。起動時のカーソルから新しい入力を読む。公式ビューアの過去5件の読み込みは採用しないため、接続前の字幕を自動公開しない。取得の間隔は1秒、通信タイムアウトは15秒。

一時的な通信エラーは1〜15秒の間隔で再試行し、受信済みカーソル・発話の状態を維持する。応答形式の変更、認可エラー、カーソルの巻き戻りは入力を停止し、`failed` を返す。終了時は閲覧参加を解除する。再起動では字幕とAdapterの状態が消える。

## 発話の変換と公開

`utteranceIdentifier` のコロンより後は断片番号であり、改版番号ではない。同じ発話の断片を番号順に連結し、Caption Relay側で変更ごとに増加する入力改版を付ける。字幕IDはトークと発話IDから作るハッシュで、閲覧リンクや話者名を含めない。

`created`・`updated`・`modified` は途中結果。`finalized` は `endOfUtterance: true` を確認し、欠けた断片がなく、すべての断片が確定した場合だけ確定入力にする。末尾の確定通知はそれまでの確定断片の終端も確定させる。`direct` はキーボード等の直接入力であり、音声認識の証拠にはしない。

無音時の `created`・`type: -1`・本文 `...` という仮データと、その取消は字幕を作らない。途中の文字入力でも `type: -1` が届くため、型だけで除外しない。空の途中結果は取消扱いにせず、観客への直前の公開文を保持する。

認識済みの発話が `removed` になった場合、取り消した断片を除いて更新する。取消済みの位置と未受信の欠落を区別し、残った断片がすべて確定していれば残存文を確定入力として送る。発話全体の明示的な取消は `removed: true` の空文・非確定入力へ変換する。手修正していない字幕は公開を取り下げる。人が保存した字幕は原文の取消後も保護し、公開文を消さない。取消済みの断片の時刻を保持し、古い再送による復活を防ぐ。

同じデータの再送は新しい改版を作らない。古い接続時刻の更新を無視し、本文が同じでも発話IDが異なれば別の字幕として扱う。本文が変わらなくても途中から確定へ変われば入力改版を進める。画像、読み仮名、翻訳、話者情報は取り込まない。

公開判定、手修正、確認モード、非表示中の発話の扱いは既存のRelayが所有する。ブラウザの下書きは明示保存まで配信しない。公開APIとSSEには字幕ID・改版・公開文だけを含める。

## 検証と限界

- [変換とRelayの回帰テスト](../backend/tests/test_udtalk.py)：断片、途中／確定、再送、逆順、取消、手修正、確認モード、非表示、公開データの境界。[実機の音声認識データ](../backend/tests/fixtures/udtalk-blackhole-speech.json)は必要な配信フィールドだけを残し、発話IDと時刻の原点を置き換えた。途中結果を公開せず、全断片の確定後だけ公開することも検証する。
- [取得処理のテスト](../backend/tests/test_udtalk_web.py)：模擬HTTP応答による通信復帰、カーソル保持、終了処理、不正応答、パスコード付きトークの拒否。これは実機接続の証拠ではない。
- 実機でWeb公開と初期化・閲覧参加・取得の応答を確認した。文字入力に加え、BlackHole経由の合成音声をUDトークが認識した。途中結果3回と2断片の確定結果から入力改版4を生成し、「キャプションリレーの音声認識テストです。本日はありがとうございます。」が実Adapter経由で操作画面と観客画面に届いた。
- 背景の実ブラウザで下書き編集と保存を操作した。下書きは観客に出ず、保存時の実APIは200、文字入力試験のSSEは公開改版2から3へ更新した。音声認識文の保存でも200とSSEの公開改版4から5への更新を確認した。手修正の後着入力・取消からの保護は回帰テストで確認しており、実アプリからの同一発話訂正では未確認。
- `bash scripts/check.sh`：フロントエンド89件、バックエンド68件成功、型検査エラー0。空の途中結果で公開文を消さないこと、先頭・中間・末尾の取消をSSEへ反映すること、未受信の欠落と取消済みの位置を区別することも回帰テストで確認した。音声認識・Web公開・試験用サーバーとブラウザは終了し、Macの入力を元のMacBook Pro Microphoneに戻した。
