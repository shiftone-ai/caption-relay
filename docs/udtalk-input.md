# UDトークの字幕を接続する

操作画面の「字幕入力の接続設定」で配信先を選ぶ。独立配信はZoom連携の送信先として受信し、UDトークへ反映する試験接続は編集用の参加リンクを使う。認識元はiOS／Android版UDトーク。Mac／Windows用の純正編集アプリには音声認識機能がない。

実装・検証の確認日：2026-10-24。

## 独立配信

1. Caption Relayを起動し、接続設定で「独立配信」を選ぶ。
2. 表示された送信先を、同じMacで動くUDトークの「Closed Caption Services」→「Zoom」に設定する。「Enable sending closed caption」を有効にする。原文を校正する場合は「Content Mode」を「Source」にする。
3. UDトークの「Send Speaker Name」を有効にした場合は、Caption Relayの「送られる字幕」で「発話者名と本文」を選び、接続を適用する。音声認識または文字入力を開始し、原文と観客画面を確認する。
4. 必要なら「Send Edited Results」を有効にする。純正が送る同一発話の訂正と空の訂正による取消も受け取る。送信対象の時間制限は[公式案内](https://udtalk.jp/post-3959/)を参照する。
5. 終了時は設定した試験用の送信先を解除し、自分で起動したサーバーを停止する。再起動と配信先の変更で送信先が変わるため、再開時は設定し直す。「送られる字幕」だけを変更した場合は送信先と受信番号を保つ。

字幕の配信と編集はCaption Relayが担当する。UDトークの共有クラウドへ閲覧参加せず受信できるが、UDトーク自体の音声認識サービスは別途必要。iPhone／iPad実機からMacのloopbackへ送ることはできない。現在の起動設定は同じMacのiOS版を対象とし、LAN公開とTLS・認証の設計は含めない。

[Zoomの送信仕様](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0060368)と[UDトークのZoom連携](https://udtalk.jp/post-3901/)を基に、UTF-8の `text/plain` POST、`seq`、`uttrId`、`lang`、最終送信番号の取得を扱う。`[Edited] `を本文から除き、同じ発話IDを更新する。空の訂正文は取消として扱い、人がこのアプリで保存した文は保護する。

直近128件の送信番号と内容で再送を判定する。異なる内容で同じ番号を使った要求は拒否し、遅れて届いた新しい発話は保持する。同じ発話の古い訂正で本文を戻さない。受信先の資格情報はサーバーごとに生成し、URLを秘密として扱う。

## UDトークへ反映する試験接続

1. UDトークで本人の試験トークを公開し、編集を許可した参加リンクを発行する。Web閲覧用・閲覧専用のリンクは使えない。参加キーの失効はUDトーク側の応答で判定する。
2. 接続設定で「UDトークへ反映（試験接続）」を選び、リンクを適用する。無効なリンクでは現在の接続を維持する。有効なリンクを適用するとZoom受信とWeb閲覧入力を止めて編集参加を始める。
3. 接続後に新しい発話を入力する。確定した字幕を選び、「保存してUDトークへ反映」で送信する。AI設定済みなら同じ経路でAI訂正も送る。
4. 純正アプリと純正Web字幕で訂正結果を確認する。このモードではCaption Relayの観客画面を使わない。ローカルの監視欄は受信文と保存済み文を示し、純正画面を再現するプレビューではない。

通信の中断とHTTP 408・429・500・502・503・504は再試行する。401・403などの拒否や不正な応答は接続を停止する。公開状態と編集権を確認し、接続を設定し直す。
5. 終了または独立配信への変更で参加を解除する。履歴と下書きは保持するが、編集参加の字幕を独立配信へ自動公開しない。

共有URLの権限と共有情報を改変せず使う。`readOnly=1` と `editOnly=1` の組み合わせは「Edit Only」として扱う。`sharingLimit` は純正クライアントが表示する情報であり、端末時計だけでキーを失効と判断しない。参加、発話の取得、ロックと通知、確定訂正、解除は[純正編集通信の解析](research/udtalk-editor-protocol.md)に基づく。字幕ID・原文改版を再確認し、ロック拒否と通信失敗を保存成功にしない。要求が受け付けられても表示到達までは保証しない。

[公式の復旧案内](https://udtalk.jp/a20261007/)では、以前のWeb閲覧URLは再発行が必要とされている。2026-10-24に新しい試験トークを作り、合成音声と手動訂正の実反映を確認した。詳細は[復旧後の実接続確認](#復旧後の実接続確認)を参照する。

## 任意のWeb閲覧入力

従来の「ウェブで公開」の閲覧リンクを読むAdapterも、独立配信で環境変数を設定した場合に使える。Zoom入力と同じトークを同時に接続すると別々の字幕として受信するため、入力経路は一つを選ぶ。以下はWeb経路の設定と2026-10-06の検証内容。公開APIとして保証された連携ではなく、公式Web表示の実装を観察した実験用接続である。

1. 音声認識を行うUDトークで、テスト専用トークを開く。Mac／Windows用の編集アプリには認識機能がない。今回の実機はApple SiliconのMac上で動くiOS版UDトークver.344。
2. 「Open Talk」→「Open Talk」→「Publish」でWeb閲覧リンクを発行する。現行Adapterはパスコード付きトークに対応していないため、機密情報を含まない接続試験で使う。
3. 閲覧リンクを環境変数に渡してサーバーを起動する。操作画面と観客画面を開き、UDトークの「Tap to Talk」から発話する。
4. `/api/source/udtalk` の `state` と `received_events`、操作画面の原文、観客画面の表示を確認する。`live` は閲覧接続が応答した状態であり、音声認識の成功を意味しない。
5. 試験終了時はUDトークの認識とWeb公開を停止し、Caption Relayのサーバーも終了する。

```bash
read -r -s CAPTION_RELAY_UDTALK_URL
export CAPTION_RELAY_UDTALK_URL
bash scripts/dev.sh
```

`read` の入力待ちで実際の `https://live.udtalk.jp/…` リンクを貼り付ける。リンクは閲覧権限を持つため、PR、ログ、スクリーンショットには含めない。設定したシェルを終了するか `unset CAPTION_RELAY_UDTALK_URL` で解除する。`.env` は起動スクリプトが読み込まない。

Caption Relayは引き続き `127.0.0.1` の単一プロセスで動かす。実機にCaption Relayの入力APIを公開する必要はない。Adapterが公式サービスへHTTPSでアクセスし、受信結果を同じプロセスの `CaptionRelay.source_event()` へ渡す。

## Macで合成音声を認識させる

今回の実機では、[BlackHole](https://github.com/ExistentialAudio/BlackHole)の2chデバイスにMacの合成音声を出力し、UDトークのマイク入力として認識させた。UDトークver.344の確認した設定には、任意の入力デバイスを選ぶ項目が見つからなかったため、Macの標準入力を一時的に変更した。出力先は合成音声の再生時に指定し、Macの標準出力は変更しなかった。

1. 現在のMacの入力デバイスを記録し、「サウンド」の入力を「BlackHole 2ch」に変更する。
2. テスト専用トークのWeb公開とCaption Relayへの接続を開始し、UDトークで日本語の認識を開始する。
3. 以下で出力デバイスを一覧にし、「BlackHole 2ch」の数値IDを入力する。IDは環境によって異なる。今回の環境では名前を直接指定すると再生に失敗したため、数値IDを使った。
4. 認識結果が操作画面と観客画面に届くことを確認する。
5. UDトークの認識とWeb公開、Caption Relayを停止し、Macの入力を記録したデバイスへ戻す。

```bash
say -a '?'
read -r BLACKHOLE_DEVICE_ID
say -a "$BLACKHOLE_DEVICE_ID" -v Kyoko -r 150 'キャプションリレーの音声認識テストです。本日はありがとうございます。'
```

2026-10-06は背面操作で認識の開始・停止とWeb公開を確認したが、文字訂正の確定は未確認だった。2026-10-24には背面操作によるキーボード入力の確定と、Caption Relayからの訂正も確認した。合成音声の認識は、物理マイクでの会話や会場の音響の検証には含めない。

参照コードのSHA-256は `6713e220d52fd75b6a7ca868a43be4cb07f43d22fae63ba41e0175502452fd45`。将来同じURLの内容が変わる可能性がある。

閲覧ページの埋め込みトーク情報を取得し、`app.udtalk.jp` に対して `checkAuth`、`initialize`、`webTalk`、`signWebTalk`、`webTalkCurrent`、`webTalkMessage` を順に使う。起動時のカーソルから新しい入力を読む。公式ビューアの過去5件の読み込みは採用しないため、接続前の字幕を自動公開しない。取得の間隔は1秒、通信タイムアウトは15秒。

一時的な通信エラーは1〜15秒の間隔で再試行し、受信済みカーソル・発話の状態を維持する。応答形式の変更、認可エラー、カーソルの巻き戻りは入力を停止し、`failed` を返す。終了時は閲覧参加を解除する。再起動では字幕とAdapterの状態が消える。

## 発話の変換と公開

`utteranceIdentifier` のコロンより後は断片番号であり、改版番号ではない。同じ発話の断片を番号順に連結し、Caption Relay側で変更ごとに増加する入力改版を付ける。字幕IDは接続ごとの識別子、トーク、発話IDから作るハッシュで、閲覧リンクや話者名を含めない。編集参加も接続ごとに識別し、再接続後の受信を古い改版や再送と混同しない。以前の接続の履歴と下書きは残すが、その下書きから新しい編集接続へ送信できない。

`created`・`updated`・`modified` は途中結果。`finalized` は `endOfUtterance: true` を確認し、欠けた断片がなく、すべての断片が確定した場合だけ確定入力にする。末尾の確定通知はそれまでの確定断片の終端も確定させる。`direct` はキーボード等の直接入力であり、音声認識の証拠にはしない。

無音時の `created`・`type: -1`・本文 `...` という仮データと、その取消は字幕を作らない。途中の文字入力でも `type: -1` が届くため、型だけで除外しない。空の途中結果は取消扱いにせず、観客への直前の公開文を保持する。

認識済みの発話が `removed` になった場合、取り消した断片を除いて更新する。取消済みの位置と未受信の欠落を区別し、残った断片がすべて確定していれば残存文を確定入力として送る。発話全体の明示的な取消は `removed: true` の空文・非確定入力へ変換する。手修正していない字幕は公開を取り下げる。人が保存した字幕は原文の取消後も保護し、公開文を消さない。取消済みの断片の時刻を保持し、古い再送による復活を防ぐ。

同じデータの再送は新しい改版を作らない。古い接続時刻の更新を無視し、本文が同じでも発話IDが異なれば別の字幕として扱う。本文が変わらなくても途中から確定へ変われば入力改版を進める。発話者名は `connected.name` から取得し、`detectedName` がある場合はその名前を優先する。名前だけの変更でも改版を進める。画像、読み仮名、翻訳は取り込まない。

公開判定、手修正、確認モード、非表示中の発話の扱いは既存のRelayが所有する。ブラウザの下書きは明示保存まで配信しない。公開APIとSSEには字幕ID・改版・公開文・公開時点の発話者名を含める。

## 復旧後の実接続確認

実接続で判明した修正は、Base64内のCRLF、Edit Onlyの権限の組み合わせ、参加応答の `users: []`、音声認識の断片IDをそのまま訂正へ使うこと。元の発話ID・話者・時刻・認識原文を保持し、変更した断片の古い読み仮名等を送信しない。複数断片の更新は順次送信であり、一部だけ受理された後の通信失敗では全体を巻き戻せない。反映済み文を取り込み、純正表示の確認を促す。

試験終了時に音声認識、Web公開、編集公開、参加、使い捨てサーバーを停止した。公開を閉じた後は、未改変の参加キーもサービスが `status: 4` で拒否した。

期限切れだった校正用キーを、以前許可された専用プロジェクトの1日・Responses限定キーで更新した。合成音声からの確定入力をGPT-5.4 Miniが校正し、2断片の元のIDで純正アプリ・純正Web字幕へ自動反映した。「あの」を除き、「13人」「午後2時」「取り消しません」を保持した。2回の応答時間は約2.059秒・約1.191秒で、各入力180・出力29トークン。[操作画面](assets/udtalk-recovery-2026-10-24/ai-relay.png)・[純正アプリ](assets/udtalk-recovery-2026-10-24/ai-native.png)・[純正Web字幕](assets/udtalk-recovery-2026-10-24/ai-web.png)・[使用量](assets/udtalk-recovery-2026-10-24/ai-writeback.json)を参照する。今回の無料枠適用と請求確定額は未確認。

文面を変えずに手動保存した場合も実サービスが受け付け、ローカルは手修正済みとなった。ロック応答待ちの取消、訂正適用後の応答喪失と再取得、他参加者のAIから同文保存を保護する処理は模擬HTTPで回帰検証した。純正編集アプリでのロック通知表示、推論中の競合と通信障害の実機試験は引き続き未確認とする。翻訳と連続運転は次節に分けて記録する。

## 発話者名の受信

Web閲覧と編集参加は、純正の `connected.name` と `detectedName` を本文から分けて受信する。名前だけの訂正と公開保留も本文と同じ発話で扱う。[発話者名のテスト](../backend/tests/test_speakers.py)で変換とSSEを検証する。2026-10-06に受信した実機データにも `connected.name` が存在した。

[公式のZoom連携案内](https://udtalk.jp/post-3889/)にも話者名の送信機能がある。「送られる字幕」は初期値を「本文のみ」とし、通常の本文を名前と誤認しない。「発話者名と本文」を選んだ場合だけ、名前と本文を最初の ` / ` で分離する。本文内に続く同じ区切りは保持する。名前を取得できなかった場合の `/ 本文` は名前なしとして扱う。区切りがない字幕も本文として保持する。

この形式は、2026-10-08にインストール済みのiOS版ver.344 / build 1を静的解析して確認した。`RTAAppDelegate` の `makeCCSendText:isEdited:`（`0x10008cf44`）と `makeCCSendText2:sendTranslation:`（`0x10008d1d0`）は、名前送信が有効な場合に接続名と本文を `%@ / %@` で組み立て、接続情報がない場合は `/ %@` を使う。Zoomの送信経路からこれらの本文生成処理への呼び出しを確認した。実行ファイルのSHA-256は `2a581ce6aed275957c58f6ad3e86d4e6faf1ac06b95bacfb04f91cf5b2f7aa70`。

この解析は名前付きの実送信を受信した証拠ではない。純正iOS版の背景操作はタイムアウトしたため、送信設定と実データの照合は未確認。名前自体に ` / ` が含まれる場合は本文との境界を特定できない。名前付き送信では名前にこの区切りを含めず、UDトーク側と受信側の設定を揃える。
