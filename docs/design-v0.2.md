## 0. 設計の要約

UDトークの認識テキストを外部連携で受け取り，不要なフィラーや繰り返しを保守的に整理し，ブラウザに字幕として配信する．運用者の操作画面と，観客が見る字幕画面を分離する．

初期版の価値は「AIが文章を美しくすること」ではなく，「読みやすく，意味を変えず，運用者が制御できる字幕を提供すること」とする．

設計の優先順位は，意味の保持，字幕の継続，低遅延，読みやすさの順とする．AI整形が利用できなくても，入力・本サーバー・表示端末が動いていれば原文で配信を継続する．

**AI整形後も，運用者が表示文を直接編集し，字幕へ反映できることを初期版の必須要件とする．** 人が確定した文はAI・上流の自動更新より優先し，再度の手修正も可能とする．

## 1. 確認済みの事実と，未確認の前提

### 1.1 外部情報

UDトーク公式サイトでは，Mac / Windows版による認識結果のリアルタイム編集と，プロジェクターやZoom / OBS向けの出力が案内されている．PC版単体には音声認識機能がない．[S1]

公式サイトにはZoomへの字幕送信に関する案内と，外部ノートテイクシステムとの連携案内がある．ただし，これらの案内は，任意の開発者が利用できる認識結果取得APIの仕様書ではない．[S2][S3]

「ケバ取り」は文字起こしの実務用語であり，サービス提供者は素起こし・整文と区別している．取り除く範囲は本アプリでも明文化する．[S4]

### 1.2 UDトーク連携の未確定事項

この調査で参照できた公開情報からは，本アプリが利用できる汎用APIのエンドポイント，認証，購読方法，発話ID，確定通知，再送仕様を確認できていない．APIが存在しないと断定するものではない．開発元による許諾・仕様提供，または利用環境での接続検証が必要．

過去の生成画像に描かれた `https://api.udtalk.jp/v1/stream`，WebSocket接続の表記，約0.8秒・98ms等の処理時間は，確認済みの仕様や実測値ではない．実装の根拠にしない．以前の短期間で実装できるという見積もりも，接続検証前のため採用しない．

以下は「認識結果を取得できる許可された連携口がある」という条件付きで進める．接続部をAdapterとして隔離し，下流は模擬入力でも検証できる構成にする．

### 1.3 初期スコープの仮定

- 日本語の会話・講演を対象とする．舞台の台詞・詩など，反復自体が表現になる場面では原文モードを選ぶ．
- 初期検証は1セッション，1入力ストリーム，主操作担当1人とする．複数の閲覧端末を接続する．
- UDトークそのものの画面書き換え，音声認識エンジンの再実装，UDトークへの書き戻しは対象外．
- UDトーク入力は認識済みのテキストを受け取る。UDトークがない場合は、マイク音声を OpenAI または Apple SpeechAnalyzer へ渡す入力部品を使う。現行実装の準備・停止・未検証の範囲は[マイク入力](microphone-input.md)を参照する。テキストだけで発話の韻律、実際の無音、誤認識の正解を確定しない。

## 2. 利用者と提供範囲

| 利用者 | 必要なこと | 初期版で提供するもの |
|---|---|---|
| 運用者 | 接続確認，原文比較，必要時の修正，出力制御 | ライブ操作画面，設定，履歴，手修正，原文への切り替え |
| 観客・参加者 | 操作を気にせず字幕を読む | 閲覧専用画面，文字サイズ・配色の調整，接続異常の表示 |
| 開発・保守担当 | 障害の切り分けと再現 | 構造化ログ，処理理由，改版記録，合成入力による再現テスト |

通常運転は自動配信とし，全発話を人が承認する運用は要求しない．人の操作は誤整形の訂正，例外対応，配信の制御に集中させる．

初期版では要約，翻訳，やさしい日本語への変換，大幅な言い換え，生成された話者推定を実装しない．「言い回しの整理」は，当初は意味を持たない重複・言いよどみの削除までとし，助詞補充や文章構造の変更を伴う整文は後続の独立したモードとする．

## 3. 情報設計と画面

### 3.1 画面の分離

| 画面 | 仮の自アプリ内ルート | 役割 |
|---|---|---|
| ライブ操作 | `/sessions/{id}/live` | 受信，整形，表示の監視と修正 |
| セッション設定 | `/sessions/{id}/settings` | 接続，整形ルール，表示，保存期間 |
| 履歴 | `/sessions/{id}/history` | 原文・表示文・訂正履歴の確認と書き出し |
| 字幕表示 | `/view/{share_code}` | 会場モニター・個人端末への閲覧専用出力 |

ルートは本アプリ側の設計案であり，UDトークのAPIを示すものではない．共有コードは閲覧専用認証に交換し，管理権限を持たせない．

### 3.2 ライブ操作画面

直近の生成画像にある「白基調，原文と整形後の比較，右側の字幕プレビュー」をたたき台にする．生成画像は視覚コンセプトであり，API仕様・性能・動作状態の証拠ではない．

中央の主領域は時刻，原文，表示文，状態の比較表とする．字幕プレビューは右側に配置する．設定と技術ログを常時大量に露出せず，必要時に開く．コピーライティング，装飾的な統計カード，AIの自信度ゲージ，大きなグラデーション，目的のないアイコンは置かない．

画面上部にはセッション名と，次の実際に判定できる状態を表示する．

- 入力：接続中／更新待ち／接続断／状態不明．最終受信時刻を併記する．
- 整形：有効／原文で継続／停止．モデルの正確さを「正常」という一語で保証しない．
- 字幕：表示中／非表示／配信終了．

上流がheartbeatを提供しない場合，テキストが届かないだけで接続断と判定しない．会話が止まっている状態と通信断を区別できない場合は「状態不明」とする．

比較表は新しい発話を末尾へ追加する．途中結果は同じ行を更新する．過去行を選択・編集中は自動追従を止め，「最新へ戻る」を表示する．整形による変更箇所だけ差分表示し，色だけに依存せず削除線やラベルを併用する．

表示文の列見出しは「表示文（編集可）」とする．各行に「編集」を置き，表示文のクリックまたはキーボード操作でも同じインライン編集欄を開けるようにする．原文列は読取専用とし，AI整形結果も比較用に保持する．「原文を採用」「前の版に戻す」「訂正として再表示」は行の補助操作にまとめる．運用者が確定した文を表示の優先値とし，後着のAI結果では上書きしない．

状態は「表示待ち／表示中／表示済み」という公開状態と，「自動整形／原文採用／手修正済み」という採用元を分けて示す．「編集中・未反映」は編集者の操作画面だけに表示する．

### 3.3 操作名と正確な意味

| 操作 | 入力取得 | 整形・記録 | 観客への表示 |
|---|---|---|---|
| 字幕を隠す | 継続 | 継続 | 非表示にする |
| 字幕を表示する | 継続 | 継続 | 操作後の新しい発話から再開する |
| 受信を止める | 本アプリの取得を停止 | 新規処理を停止 | 最後の字幕を保持し，停止状態を示す |
| 自動整形を切る | 継続 | 原文を採用 | 原文で継続する |
| 自動追従を止める | 継続 | 継続 | 観客への表示は変えない |
| セッションを終了 | 停止 | 新規処理を終了 | 終了状態を通知し，新規配信を止める |

「字幕を隠す」は録音・記録やAI送信を停止する操作ではないことを明示する．再表示時には非表示期間の発話を一括再生せず，非表示中に開始された発話も自動では公開しない．発話境界を安全に識別できない入力形式では，再表示時に新しい境界を作れるまで待機する．

「受信を止める」はUDトークのマイク停止を意味しない．上流機器を遠隔停止できるAPIが確認されない限り，その機能は提供しない．

### 3.4 AI整形後の手修正（初期版必須）

#### 編集の基本動作

AI整形後の「表示文」をそのまま編集できる．整形前だけの修正や，別の履歴画面での事後修正に限定しない．表示待ち・表示中・表示済み・手修正済みの字幕を対象とする．AIが失敗して原文を採用した字幕も，同じ操作で編集できる．

1. 対象行の「編集」，表示文のクリック，またはフォーカス後の編集操作で，表示文を入力済みのテキストエリアを開く．
2. 原文とAI整形結果を参照しながら加筆・削除・置換する．手修正はケバ取りの削除制約に限定せず，誤認識された固有名詞や数値なども運用者の判断で直せる．表示に使う文字列としての検証・権限確認は適用する．
3. 「修正を反映」（表示済みの過去行では「履歴を保存」）で確定する．「キャンセル」は入力中の変更を捨て，現在の保存済み表示文へ戻る．
4. 保存成功後は「手修正済み」と表示する．人が直した字幕も，同じ手順で何度でも再編集できる．

入力中の下書きは観客へ送らない．打鍵ごとの自動公開は行わず，サーバーが受理した確定文だけを配信する．下書きは編集中のブラウザのメモリに保持し，初期版では端末への永続保存を行わない．ページ再読み込み・閉鎖時の下書き復元は保証しない．

編集開始時に選択行の高さ・位置と下書きを保持し，自動追従を止める．新しい発話の受信・自動整形・観客向け配信は継続する．追従停止を配信停止に連動させない．未反映の下書きを別行の選択や画面移動で黙って捨てない．

#### 修正文をどこに反映するか

| 対象の状態・操作 | 保存と公開の動作 |
|---|---|
| 表示待ちの字幕に「修正を反映」 | 手修正文を採用版として保存し，元の公開順と表示可否に従って公開する．手修正で順番を追い越さない |
| 表示中の字幕に「修正を反映」 | 同じ字幕IDの新しい改版として置き換え配信する．新規発話として追記しない |
| 表示済みの過去字幕に「履歴を保存」 | 訂正履歴を保存する．閲覧端末がその字幕を履歴として保持していれば同じIDを更新するが，現在の表示領域へ呼び戻さず，スクロール位置を変えない |
| 過去字幕に「訂正として再表示」 | 確定済みの修正文を，対象発話を参照する訂正表示として明示的に公開する．新しい発話と誤解させない |
| 非表示中・セッション終了後の修正 | 履歴・採用版の更新に限定する．修正や再表示操作で非表示・終了状態を解除しない |

編集中に対象字幕が画面から流れた場合，保存時点のサーバー側表示状態に従う．通常の反映操作は過去字幕を再表示せず，操作画面には「履歴に保存しました．現在の字幕は変更されていません」と結果を示す．表示状態だけが変わったことは本文の編集競合とはしない．

観客側には，字幕の訂正が分かる控えめな「訂正」の表示を付ける．入力中の下書き，操作者名，編集差分，内部的な手修正フラグは配信しない．複数端末へ同じ確定改版を配信し，切断端末は復帰時に同期する．保存成功を全端末への到達確認とは扱わない．

#### 人が確定した内容を保護する

手修正の保存で，対象字幕を自動上書きから保護する．後着のAI結果，再試行結果，上流の原文更新は候補・原文として保持し，操作画面に通知するが，手修正文を差し替えない．他の発話の自動整形は継続する．

編集開始後にAI結果・原文・別タブの修正が届いても，入力中の下書きを書き換えない．保存時は，編集開始時に確認した表示文の改版と原文の改版を照合する．変わっていれば競合を表示し，下書きを保持したまま最新内容と比較できるようにする．最新版を確認した運用者の再適用でのみ保存する．強制上書きや自動マージはしない．

「原文を採用」「前の版に戻す」も，内容を確認して新しい手動改版として保存する．過去の改版を削除せず，自動上書きからの保護も解除しない．AIの再実行は候補の作成にとどめ，人の明示的な採用なしに手修正を消さない．

#### 保存・入力時の注意

保存は明示操作のみとする．Enterは改行，反映はボタンまたはCtrl / Cmd + Enterとする．IME変換中のキー操作や変換確定を送信扱いにしない．EscはIME処理を優先し，未反映の変更がある場合は破棄確認を経て編集を閉じる．

通信エラー時は下書きを残し，「未反映」と再試行操作を表示する．タイムアウトでサーバー側の受理が不明な場合も，成功と決めつけない．同じ冪等キーによる照合・再試行で保存結果を確定する．空白だけの手修正は受け付けず，「字幕を隠す」等の別操作へ誘導する．

### 3.5 字幕表示画面

観客用には管理UI，原文との差分，接続先，処理ログを送らない．AI整形文・原文採用文・人が確定した修正文のうち，公開を許可した字幕だけを配信する．

初期表示は高コントラストの黒背景・白文字を基本とし，白背景・黒文字も選べる．会場用は数行の大きな文字，個人端末用は直近の発話履歴を読める表示とする．文字サイズ・行間・余白は調整可能にする．これらの値は実機と会場で検証する設定値であり，現時点で最適値を断定しない．

生成中の文章を一文字ずつ観客へ配信しない．検証された字幕単位を表示し，画面の長さに応じて分割する．文字を小さくし続けたり，長文の後半を黙って切り捨てたりしない．表示速度の問題が出たときは，運用者へ滞留を通知する．ライブ位置へ飛ばす場合は明示操作にする．

通信断では最後の字幕を残しつつ「字幕の接続が切れました」と表示する．断線した古い文を，現在の発話に見せ続けない．復帰時には現在のスナップショットを取得し，過去の大量再生は行わない．

通常文字のコントラストは4.5:1以上を検証基準とする．状態は色だけで区別しない．キーボード操作，フォーカス可視化，拡大，動きを減らす設定を検証する．色とサイズだけでアクセシビリティ対応済みとは判定しない．[S6]

W3Cのライブ字幕の説明には，発話だけでなく話者や重要な非言語音の情報も含まれる．本アプリはテキスト後処理だけなので，入力にない笑い・拍手・効果音・話者を自動で復元できるとは主張しない．必要な場面では運用者の補足入力を後続要件とする．[S7]

### 3.6 整形設定の文言

主要モードは「原文」と「ケバ取り」の2つとする．

「ケバ取り」の説明文：

> 「えー」「あのー」など，意味に影響しない言いよどみや不要な繰り返しを整理します．

詳細設定に「フィラーの整理」「不要な繰り返しの整理」「句読点の調整」を置く．「数値を保持する」「否定を保持する」「固有名詞を保持する」は任意のON/OFFではなく，常時守る制約とする．

大きな「整形の強さ」スライダーは置かない．強くすると何が変わるか不明確になるため，意味の異なる処理は独立したモードとして評価する．

## 4. 整形処理の契約

### 4.1 3種類の重複を区別する

1. 通信の再送：同じイベントを再受信したもの．識別子で排除する．
2. 認識途中の更新：同じ発話の文章が増えたり置き換わったりするもの．同じ発話の改版として扱う．
3. 実際の発話内の反復：話者が言い直したり強調したりしたもの．文脈に基づく整形候補にするが，無条件に削除しない．

文章が同一という理由だけで重複排除しない．別の話者による「はい」や，時間をおいて繰り返した説明は別の発話として残す．

### 4.2 自動処理で許可する範囲

意味のないフィラー，重複した語句，必要最小限の句読点調整に限定する．判断が曖昧なら原文を採用する．

数値・単位・日時，人名・組織名・作品名，否定，推量，強調，話者の区別を壊さない．音声認識の誤りを文脈だけから正解と決めつけて修正しない．「100万円，いや10万円」のような訂正は，初期版では両方を残す．

### 4.3 LLMには自由作文させない

ケバ取りでは，対象原文に対する削除区間と，許可された句読点調整の候補を返させる方式を第一候補とする．サーバーが原文へ編集を適用して表示文を作り，モデルの自由な全文出力をそのまま公開しない．

処理要求には，対象発話，入力改版，入力ハッシュ，適用ルール版を含める．文脈として過去の少数発話を参照させても，編集対象は指定した発話だけとする．

範囲外・重複する編集区間，許可外の文字追加，保護対象の変更，過剰な削除，形式違反は拒否する．文字位置の定義はサーバー内部でUnicodeコードポイントに統一し，ブラウザには表示用の差分セグメントを返す．JavaScriptの文字列位置と混在させない．

ただし，削除だけでも意味が変わることはある．検証器は意味保存の完全保証ではなく，事故範囲を狭める仕組みである．実データによる評価，人の介入，原文モードを残す．モデル自身が返す自信度を唯一の公開可否条件にしない．

フィラーだけの発話が空文字になった場合は，新規字幕を追加しない．空文字を「画面を消す命令」として扱わない．

### 4.4 暫定の例示テスト

すべて設計用の合成例であり，性能を検証済みという意味ではない．

| 入力 | 期待する処理 |
|---|---|
| えー，本日は，本日はお集まりいただきありがとうございます． | 本日はお集まりいただきありがとうございます． |
| 次に，あのー，作品を紹介します． | 次に，作品を紹介します． |
| 絶対に，絶対に必要です． | 強調の可能性があるため保持 |
| 100万円，いや10万円です． | 訂正と数値を保持 |
| 安全だとは思いません． | 否定と態度を保持 |
| 来場者が操作できると思います． | 「と思います」を保持 |
| 話者A：はい．／話者B：はい． | 両方を保持 |
| あの作品は，えー，展示中です． | 指示語「あの」は保持，フィラーのみ候補 |
| えー，あのー． | 文脈上フィラーのみなら出力を追加しない |

## 5. システム構成

### 5.1 論理構成

入力Adapter，発話状態管理，整形処理，検証，公開管理，操作API，字幕配信を1つのバックエンド内の独立モジュールとして構成する．最初からマイクロサービスには分けない．

処理の順序は以下とする．

`UDトーク連携 → 入力正規化 → 発話・改版管理 → 整形候補 → 検証 → 出力確定 → ブラウザ配信`

原文フォールバックは整形候補・検証を迂回し，同じ公開管理を通る．運用者の手修正も公開管理を通す．ブラウザごとにAI処理を実行せず，同じ確定字幕を全表示端末で共有する．

### 5.2 採用候補

| 層 | 初期採用案 | 理由・制約 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | 操作画面と閲覧画面で状態モデル・表示部品を共有する |
| バックエンド | Python + FastAPI | 入力購読，整形，操作API，配信を集約する |
| ブラウザ向け配信 | SSE | 主なデータ方向をサーバーからブラウザへ限定する |
| 操作 | HTTP API | 手修正・設定・配信制御を明示的な更新操作にする |
| 永続化 | 単一プロセスのPoCはSQLiteを候補とする | 多重起動・複数ワーカー運用をしない |
| 本番の永続化 | PostgreSQLを候補とする | 複数セッションや運用要件に応じて選ぶ |
| AI | 交換可能なLLM Adapter | モデル，データ保持条件，日本語品質，遅延を実測して選定する |

React，Vite，FastAPIの公開資料を参照しているが，ここでの組み合わせは本プロジェクトの採用案である．バージョンは実装開始時に固定する．[S9][S10][S11]

SSEには再接続とLast-Event-IDの仕組みがある．ただし，欠落回復・イベント再送・重複排除まで自動で保証されるわけではないため，サーバー側にイベント保持と復帰手続きを実装する．UDトーク側の通信方式がWebSocketであると仮定するものではない．[S5]

### 5.3 配置

公開インターネット上で観客の端末から閲覧する場合は，HTTPSで公開した単一バックエンドとする．操作画面は認証必須，閲覧画面はセッション限定の閲覧権限とする．

上流連携が会場LAN内に限定される場合のみ，会場側に小さな入力Bridgeを置き，バックエンドへ認証付きで送る構成を追加する．実際のUDトーク連携仕様が確認される前に，Bridgeの必要性を決めつけない．

本体がローカルで動いても，UDトークの認識や選定LLMが外部サービスに依存する場合はオフライン完結ではない．UIをローカルにしただけで通信依存がなくなるとは説明しない．

## 6. 入力Adapterとデータモデル

### 6.1 Adapterの機能申告

接続部は少なくとも以下の有無を申告する．未知の能力をあるものとして埋めない．

| 能力 | 使い道 | 無い場合 |
|---|---|---|
| 安定した発話ID | 同一発話の更新判定 | 代替の区切り方を実機検証する |
| イベントID・改版番号 | 再送排除・順序制御 | ローカル改版だけで上流の再送を完全識別できるとは主張しない |
| 途中／確定通知 | 整形開始の判断 | 更新停止からの仮安定判定を別扱いにする |
| 話者ID・話者名 | 話者表示 | 話者名を生成しない |
| 発話時刻 | 音声との対応 | 受信時刻として保存し，発話時刻と混同しない |
| 再接続カーソル | 欠落回復 | 復元できない区間を欠落として記録する |
| 編集・削除イベント | 上流訂正の追従 | 過去字幕の正確な同期に制限があると表示する |
| heartbeat | 生存確認 | 無発話と断線の区別に限界があることを表示する |

上流が提供しないVAD情報を，テキストだけから実測したかのように扱わない．受信の途切れは音声の無音とは限らない．

### 6.2 内部データ

| エンティティ | 主な情報 |
|---|---|
| Session | セッションID，開始・終了，運用設定版，保存期限，表示状態 |
| SourceConnection | 接続方式，機能申告，接続世代，受信カーソル，認証参照 |
| InputEvent | 取得したイベントと由来，受信順，受信時刻，上流識別子，重複判定結果 |
| UtteranceRevision | 発話ID，入力改版，原文，話者，途中／仮安定／上流確定，元イベント参照 |
| FormattingAttempt | 入力改版，ルール版，モデル版，編集候補，検証結果，期限，エラー区分 |
| CaptionRevision | 採用した表示文，採用元（AI／原文／手修正），入力由来，手動保護フラグ，出力改版，直前の改版，編集者，編集日時 |
| PublicationEvent | 公開イベント連番，字幕ID，操作種別，出力改版，配信対象，公開時刻 |
| AuditEvent | 誰が何を変更したか，変更前後の版，時刻 |

原文，AI候補，実際の表示文を別に持つ．原文は保持期間内で改変しない．手修正も原文を書き換えず，新しい表示改版として記録する．

入力の改版番号と公開イベント連番は別物にする．入力が10回更新されたことと，字幕が10回公開されたことを混同しない．

編集中の下書きと，保存済みCaptionRevisionも別物とする．CaptionRevisionの保存だけで未公開・非表示の字幕が公開されることはない．履歴修正は元の字幕IDを更新するイベントとし，「訂正として再表示」だけが独立した表示イベントを作る．

## 7. 状態・順序・競合

### 7.1 基本状態

`受信中 → 整形対象として準備完了 → 整形中 → 検証済み／原文採用 → 公開済み`

上流の確定通知を得られる場合はそれを優先する．得られない場合，更新停止による「仮安定」は上流確定とは別の状態とする．この経路を自動公開に使う可否は入力PoCで判定し，未検証のまま有効化しない．

途切れない長文や途中結果の継続更新は，安定した接頭部分だけを区切れることを入力PoCで検証する．分割が安全にできない場合は，不確定な単語を確定字幕として公開せず，制限を明示する．

### 7.2 古いAI結果を採用しない

整形要求を出したときの入力改版と，結果到着時の現行改版を比較する．すでに新しい原文へ更新されていたら，古い候補を採用しない．

発話1より発話2のAI処理が先に終わっても，公開順を逆転させない．発話1が期限を超えたら原文で公開し，発話2へ進む．

### 7.3 手修正・原文採用の優先

運用者が手修正した文と，期限切れで原文採用した文は，後から届いたAI結果では変更しない．再整形や取消は明示操作にする．

手修正後に上流原文が変更された場合は，変更があったことを操作画面に示す．手修正を黙って破棄せず，運用者が訂正内容を照合する．

入力中の下書きの保護と，保存済み手修正文の保護は別に行う．編集を開いたことだけではサーバー全体や字幕配信をロックしない．保存時の改版照合と手動保護フラグの設定は同じトランザクションで行い，AI採用・上流の自動反映も同じ条件付き更新を使う．人とAIが同時に保存しても，手修正文への自動上書きを許さない．

手修正がない字幕への上流修正については，現在画面に残っている字幕を訂正表示として更新する．手修正済みの字幕は自動で置換せず，前段の照合ルールに従う．過去へ流れた字幕は履歴で更新を知らせ，必要時に運用者が「訂正として再表示」する．後着のAI候補を上流修正と混同しない．

### 7.4 公開と永続化

出力改版の保存と公開イベントの記録は同じトランザクションで行う．ネットワークへ先に送って後から保存する順序にしない．配信部は保存済みイベントを読む．

初期構成ではセッションの処理所有者を1つに限定する．複数ワーカーへ拡張する場合は所有権・排他・失効を別途実装する．インメモリ状態を複数ワーカーで別々に持つ構成は禁止する．

### 7.5 表示端末の復帰

表示状態のスナップショットと，同じ時点の公開カーソルを返す．クライアントはそのカーソル以降を購読する．スナップショット取得と購読開始の間のイベントも保存済みイベントから補えるようにする．

クライアントは公開イベントIDと字幕改版を照合し，同じイベントを二度適用しない．保持範囲を超えたカーソルの場合は現在のスナップショットへ同期し，古い字幕を無制限に再生しない．

## 8. 自アプリのAPI契約案

以下は本アプリで実装するAPIの案であり，UDトークが提供しているAPIではない．認証・入力検証を全操作へ適用する．

| API | 権限 | 用途 |
|---|---|---|
| `POST /api/sessions` | 運用者 | セッション作成 |
| `POST /api/sessions/{id}/source/test` | 運用者 | 接続仕様に応じた接続試験 |
| `POST /api/sessions/{id}/commands` | 運用者 | 表示／非表示，受信停止，整形切替，終了 |
| `GET /api/sessions/{id}/state` | 運用者 | 操作画面のスナップショットとカーソル |
| `GET /api/sessions/{id}/events` | 運用者 | 操作画面向けSSE |
| `PATCH /api/sessions/{id}/captions/{caption_id}` | 運用者 | 表示文・原文の対象版を指定した手修正．保存と現在表示への条件付き反映 |
| `POST /api/sessions/{id}/captions/{caption_id}/republish` | 運用者 | 過去字幕を訂正として再表示 |
| `GET /api/view/state` | セッション限定閲覧 | 公開字幕だけのスナップショット |
| `GET /api/view/events` | セッション限定閲覧 | 公開字幕だけのSSE |
| `POST /api/sessions/{id}/exports` | 運用者 | 保持期間内の履歴書き出し |

更新系はクライアントの重複送信に備えて冪等キーを受け付ける．手修正にはtext，base_revision（表示文），base_input_revision（確認済み原文）を必須とする．競合時は409と最新の改版・本文を返し，保存・公開とも行わない．操作者は認証情報から決定し，クライアント申告だけでは決めない．

通常の手修正は，採用版を更新し，公開済みの同じ字幕IDを訂正する．現在表示に含まれている場合はその場を置き換え，過去字幕では履歴だけ更新する．未公開字幕は元の公開条件を維持し，訂正イベントによって新規公開しない．非表示中・終了後は管理記録だけを更新し，本文を観客へ配信しない．公開済み改版と最新の採用版が異なる場合は，操作画面で区別する．再表示は別APIによる明示操作とする．

成功レスポンスには保存した改版と反映結果（表示待ちへ採用／同じ字幕を訂正／過去字幕の履歴更新／非公開の記録更新）を返す．保存と許可された公開イベントの記録を原子的に行う．保存後に通信が切れた場合，同じ冪等キーと同一内容の再試行には元の結果を返し，同じ訂正を重ねて作らない．冪等キーの照合は，受理済み操作について改版競合を再判定する前に行う．

閲覧APIは公開専用のデータモデルから応答する．管理用イベントを配信してブラウザ側で隠す方法は採用しない．

## 9. 遅延・障害・監視

### 9.1 暫定の目標と計測境界

以下は設計目標であり，実測値でも提供保証でもない．

- 整形対象として準備完了した時刻から，公開イベント保存まで：p95で1.5秒以内を検証目標とする．
- 同じ区間で2秒の公開期限を設け，期限内に整形を採用できなければ原文へ切り替える．待ち行列の時間も含む．
- 途中結果の安定待ち，上流の音声認識時間，配信回線，端末描画時間は別に記録する．

発話時刻が得られない場合，受信からの処理時間を「話し始めてからの遅延」と表記しない．端末間の時計を比較する場合は時刻同期または測定誤差を考慮する．

### 9.2 障害時の方針

| 状況 | 動作 |
|---|---|
| AIのタイムアウト・レート制限 | 対象発話は原文で配信．回復まで原文モードで継続 |
| AIの不正な編集・形式違反 | 候補を拒否し原文を採用．理由を運用者へ表示 |
| 入力の再送 | 確実に同じイベントと識別できるもののみ排除 |
| 上流接続断 | 再接続し，カーソルがある場合に欠落回復．復元不能区間は記録 |
| 閲覧端末の接続断 | 最後の字幕と接続異常を表示．復帰後スナップショット同期 |
| 処理滞留 | LLMの待ち行列を増やし続けず原文へ切替．字幕の黙った破棄は禁止 |
| 本サーバー停止 | 配信を継続できない．永続状態から復帰し，未公開分の期限を再判定 |
| セッション終了後のAI応答 | 保存済み終了状態を確認し，公開しない |

### 9.3 監視項目

入力最終受信時刻，入力接続状態，処理待ち数，整形対象から公開までの時間，AI失敗率，原文採用率，候補拒否理由，接続中の表示端末数，公開イベント連番を取得する．取得できない数値は空欄または「未計測」とし，ダミーの数値を実測表示に混ぜない．

ログに全文やAPIキーを無条件で記録しない．テキスト調査が必要な場合は，アクセス制御されたセッション記録を参照する．

## 10. セキュリティとデータの扱い

上流の認証情報とLLMの認証情報はバックエンドに保持する．閲覧URL，配信イベント，HTMLソースへ含めない．接続先は管理者が定める許可先に限定し，任意のURLへサーバーから接続できる設定にはしない．

音声認識された発話は信頼できない入力として扱う．「以前の指示を無視して」と話されても，整形指示に昇格させない．指示と本文を分離し，LLMのツール呼び出し・外部操作を無効にし，出力を検証する．これはプロンプトインジェクションへの防御の一部であり，単一のプロンプトだけで安全を保証しない．[S8]

画面にはプレーンテキストとして表示し，原文をHTMLとして解釈しない．セッションIDの推測だけで記録や配信にアクセスできないようにする．共有コードは期限・対象セッション・読取専用権限に制限し，失効可能にする．共有コードを含むURLはログやRefererに残さない構成を検討し，同一オリジンの閲覧用Cookieに交換する．

保存期間は初期検証では「セッション終了から24時間」を暫定値とし，開始前に選択・表示できるようにする．原文・候補・修正履歴も同じ保持方針に従う．監視ログやバックアップに全文を残して削除を実質無効にしない．書き出し後の利用者のコピーまで消去できるとは説明しない．

外部LLMへテキストを送信する事実，送信先，送信範囲，保持条件を導入前に確認する．UDトーク側のプライバシー条件だけで，新しい送信先の扱いまで決まると説明しない．

## 11. 検証計画と受け入れ条件

### 11.1 入力PoCの完了条件

許可された連携で実際のテキストを受け取り，途中更新，確定，修正，再送，切断，復帰のサンプルを取得する．利用できる機能とできない機能をAdapterの機能申告へ反映する．

認識結果の同一発話を追跡できない場合は，その制限を残して下流に見せる．模擬入力が動いても「UDトーク接続済み」とは判定しない．

### 11.2 必須テスト

| 項目 | 受け入れ条件 |
|---|---|
| 合成例のケバ取り | 期待する削除を行い，意味のある語を変えない |
| 数値・否定・推量・強調 | 保護ケースを改変しない |
| 同一イベント再送 | 同じ字幕を追加表示しない |
| 別発話で同じ文章 | 正当な反復を消さない |
| 途中結果更新 | 同じ発話の改版として扱い，二重追記しない |
| 古いAI結果 | 新しい原文・手修正文へ上書きしない |
| AI処理の完了順逆転 | 発話の公開順が逆転しない |
| AI停止・期限超過 | 入力が届く限り原文公開へ切り替わる |
| 空の整形結果 | 画面を消す命令と誤解しない |
| 整形後の直接編集 | ライブ操作画面の表示文から，AI整形後・原文採用後のどちらも編集できる |
| 手修正文の再編集 | 人が直した字幕を再度修正し，新しい手動改版として保存できる |
| 編集下書きの非公開 | 打鍵・IME変換中の文字が観客向けイベント・画面に現れない |
| 表示中の修正反映 | 同じ字幕IDが置換され，別の発話として二重追記されない |
| 過去字幕の修正 | 履歴は更新されるが現在画面へ割り込まない．明示的な再表示時だけ訂正表示する |
| 保存直前に対象が表示済みへ移動 | 履歴だけ更新し，古い字幕を再表示しない．操作結果を通知する |
| 編集中の継続配信 | 下書き・カーソル位置を守りながら，新しい発話の配信は継続する |
| 手修正とAIの同時保存 | 手動保護と改版照合により，確定した手修正文を自動更新が消さない |
| 手修正競合 | 表示文または原文の対象版が変われば409と最新内容を示す．下書きを失わず再確認できる |
| 手修正後の上流更新 | 原文の変更通知だけを行い，人の採用文を置換しない |
| 保存通信失敗・応答消失 | 下書きと未反映表示を保持し，同じ冪等キーで結果を照合・再試行できる |
| 手修正の取消・前版採用 | 新しい手動改版を作り，監査履歴と自動上書き保護を維持する |
| 非表示・終了後の手修正 | 履歴を保存しても観客向け表示・配信を再開しない |
| 非表示から再表示 | 非表示期間の内容が勝手に再公開されない |
| 管理画面の自動追従停止 | 観客向け配信には影響しない |
| SSE切断・再接続 | 重複適用せず，現在状態へ回復する |
| スナップショットと購読の間の更新 | 保存済みカーソルから回復できる |
| 上流の復元不能区間 | 無かったことにせず，運用者へ欠落を示す |
| セッション終了後の後着応答 | 字幕を再開しない |
| 攻撃的な発話・HTML文字列 | 指示実行・HTML解釈をしない |
| 閲覧権限 | 原文履歴・管理操作・接続秘密を取得できない |
| IME入力 | 変換確定で誤送信しない |
| 長時間運転 | 原文数に比例してDOMを増やし続けず，表示とメモリ使用を測定する |
| 表示とアクセシビリティ | 拡大，キーボード，コントラスト，長文折返しを実機確認する |
| 保存期限 | 原文・改版・候補・閲覧権限の期限処理が仕様どおりである |

意味保存の評価は，固定ケースで重大誤変更0件を初期の受け入れ条件とする．これは評価セット内の結果であり，未知の発話でも誤変更が0件だという保証にはしない．実際の利用者・運用者による読みやすさと負担の確認を行う．

## 12. 実装Issue案と順序

| ID | Issue | 完了条件 | 依存 |
|---|---|---|---|
| CR-01 | UDトークの連携仕様・利用条件を確認する | 接続方法，認証，イベント形式，更新・再送の扱いを実データで記録 | 外部仕様・接続環境 |
| CR-02 | 模擬入力Adapterとイベントfixtureを作る | 途中更新・重複・逆順・断線・復帰を再現 | なし |
| CR-03 | セッション・発話改版・公開イベントを実装する | 原文不変，手修正優先，順序保証のテスト合格 | CR-02 |
| CR-04 | 原文だけで操作画面・閲覧画面と直接編集を通す | 受信から表示，インライン編集，明示反映，再編集，非表示，再接続まで動く | CR-03 |
| CR-05 | ケバ取り候補と検証器を実装する | 合成例，意味保持，形式違反，フォールバックのテスト合格 | CR-03 |
| CR-06 | AI整形後の直接編集・公開反映と競合保護を統合する | 下書き非公開，手修正の再編集，訂正配信，原文更新競合，後着AI，通信再試行，非表示・終了時保護のテスト合格 | CR-04，CR-05 |
| CR-07 | 実際のUDトークAdapterを接続する | CR-01の入力仕様に適合し，取得・改版・復帰を実測 | CR-01，CR-03 |
| CR-08 | 権限・保存期限・監視を仕上げる | 閲覧分離，秘密情報保護，失効，期限処理を検証 | CR-04 |
| CR-09 | 会場リハーサルを行う | 実際の回線・画面・発話速度で可読性と遅延を記録 | CR-06〜08 |

着手順は，CR-01の外部確認と並行してCR-02〜04を進め，AIなしでも字幕が通る骨格を先に作る．API仕様が得られない間は模擬入力で下流の検証を進めるが，実接続の完了とは扱わない．

## 13. 後続で確定する事項

UDトーク側APIの利用条件，入力イベントの正確な形式，本番の配置，利用者数・接続端末数，保存期間，LLMの提供元とデータ保持条件，数値目標の妥当性を確定する．

これらはすべて同じ重さではない．本番接続のブロッカーは入力APIの許諾とイベント仕様．画面設計・改版モデル・整形契約・模擬入力テストは独立して進められる．
